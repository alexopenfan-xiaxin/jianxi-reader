# 简兮阅读器 3.0 准入评估与路线图

> 评估基线：`flutter/` @ `84c6f9d`（工作区 HEAD，版本仍是 `2.9.9+199`；tag 停在 `0e3b232`；73 次提交 / 6 个 tag）
> 评估方式：只读静态审计（本机无 Flutter/Dart SDK，未运行构建与测试）
> 报告日期：2026-10-29

> **定稿（2026-10-29）**：`3.0.0+300` · Android only · A/B/C/D/G + E-min/F-min · 9–11 周 · 不做导出/备份/回收站、桌面、iOS、云同步、AI、EPUB/PDF · 发布私钥仅存 GitHub Secret，禁止删除/轮换/迁移。

> 本文含发布/供应链细节（密钥托管、签名、更新链），建议作为内部文档，不随公开仓库发布。

## 0. 结论

**现在不建议直接发 3.0。**

不是功能不够——2.9.9 的功能密度已经超过大多数同类阅读器；而是四张底牌还没凑齐：

1. **数据没有退路**：没有导出、迁移回退、删除撤销。一次坏升级或误删，书签/进度/标签就可能消失，而且无法挽回。
2. **改动没有证据**：59 个用例对 244 个类；阅读器、导入、更新这些最危险的链路没有直接测试；CI 不构建 Android。
3. **发布没有信任**：缺密钥会回退 debug 签名并继续发布；应用内更新对更新主机放行任意证书、下载后不校验摘要、版本头缺失时默认"有新版本"。
4. **产品没有主张**：书签/历史只写不读，3.0 到底解决什么，还没有一句话能说清。

建议用 **9–11 周**（保守 12–14 周）完成 A/B/C/D/G + 最小守卫，直接发 `3.0.0+300`；alpha/beta 用 `3.0.0-alpha.N+29x` 预热，不做 2.9.10 公开止血包。如果两周内必须发版，请叫它 `2.10.0`——那不是 3.0。

> 3.0 是否合格，不看功能清单，看 **3.1 的 5 步演示**；任何一步不成立，都只是 2.9.10 换了个号。

### 明早先看这 10 条

1. 当前 `main` 已经**不可发布**：`v2.9.9+199` 指向 `0e3b232`，HEAD 已领先 2 个提交；现在跑 `publish.yml` 会在 tag 校验处失败。
2. 发布链有两个 P0：缺 keystore 时 release 回退 debug 签名且继续发布；更新链路无摘要校验，中间人可投递 APK（安装器验签后通常表现为更新失败/被诱导重装）。（最新 `2.9.9+199` 包已核验为自定义证书，不是 debug；风险在"未来某次缺 secret 时静默回退"，见 2.4。）
3. 数据层有三个高置信问题：非 Android 死路径"移出"会删原文件（Android 不受影响，删掉即可）；任一 JSON 单条损坏会导致整文件被清空并在下次写入时覆盖；删除失败后书签/历史成永久孤儿。
4. 阅读进度会被"打开即退出"清空：dispose 用当前像素 0 保存，而服务层把 `<1%` 当作"删除进度"。
5. 两个功能"写得进、读不出"：书签只能加，没有列表/跳转/删除入口；阅读历史每次打开都记录，但从未展示。
6. 核心承诺"格式原貌"在导入场景是破的：文件夹导入会扁平化，且只复制 `.md/.html`，相对路径图片/CSS 全部失效。
7. 单个"移出"没有确认、没有撤销；批量"移出"却有确认——同类破坏性操作不一致。
8. 包体里 25.5 MB 是同一款字体，约占 APK 的一半；字体授权文件不在仓库。
9. 可访问性近乎空白：全仓 0 处 `textScaler` / `disableAnimations`；次要文字对比度 3.94–4.29:1，低于 AA 的 4.5:1。
10. 3.0 的机会不是再加格式，而是把"导入 → 阅读 → 找回 → 不丢"这条链路做闭环。

## 1. 什么叫"合格进入 3.0"

### 1.1 版本号是一种承诺

2.x 的 199 个 build 证明的是"持续交付"；3.0 必须是一次**断点**。断点至少要满足一条：

- 数据模型发生不可逆升级，需要迁移；
- 交互/信息架构重做，用户需要重新学习；
- 平台或格式边界扩张。

如果只是修 bug、加小功能，那是 2.10，不是 3.0。**建议把 3.0 绑定到"数据模型 v1 + 文档包"上**，这样版本号才站得住，而不是营销数字。

### 1.2 四张契约

| 契约 | 对用户的承诺 | 对团队的承诺 | 失败的样子 |
|---|---|---|---|
| **数据** | 升级不丢，坏了能救，误删可撤销 | schema 版本、迁移、内部快照、事务 | 升级后书签没了 |
| **质量** | 核心链路每次改动都有证据 | 关键路径测试、覆盖率底线、迁移/损坏演练 | 改 A 坏 B，靠用户报 bug |
| **产品** | 一句话说清 3.0 解决了什么 | 范围裁剪、验收场景 | 功能很多，没有一个记得住 |
| **交付** | 每个版本可追溯、可验证、可回滚 | 单一版本源、签名、摘要、灰度 | 发出去的包没人能确认是不是自己打的 |

### 1.3 对照：现在缺哪张

- **数据**：无 schema、无迁移、无回退、无撤销 → 不合格。
- **质量**：无集成测试、无覆盖率、无 Android 构建门禁 → 不合格。
- **产品**：3.0 主张未定义，书签/历史未收口 → 不合格。
- **交付**：签名回退、无摘要、无回滚 → 不合格。

四张全缺，所以"直接改号"不是 3.0，是把 2.x 的债带进下一个大版本。

### 1.4 两条路线

| | 路线 A：3.0-proper（推荐，定稿） | 路线 B：2.10-lite（止血） |
|---|---|---|
| 周期 | 9–11 周（含 beta 10–12；一个人 12–14） | 2 周 |
| 内容 | A/B/C/D/G + E-min/F-min | 只修发布/数据/合规硬伤，不加数据模型 |
| 版本号 | `3.0.0+300`（alpha/beta 29x） | `2.10.0+300` |
| 风险 | 范围膨胀、迁移 bug、测试被压缩 | 用户无感，债继续滚 |
| 适用 | 想做一个能撑两年的版本 | 两周内必须交付 |

**建议选 A，但把 A 切成可随时停车的阶段**；如果中途资源不够，至少完成 Phase 0–1，退回 `2.10.0` 也是一个干净的版本。**E-min/F-min 不能为零**：它们不是功能，是让 A/B/C/D/G 敢发的 1.5 天 + 2 周。

> 已核验：GitHub Release 的 `v2.9.9+199` APK 使用自定义证书 `CN=Jianxi Reader, OU=Development, O=Jianxi, C=CN`（SHA-256 `b76b05e9…`），不是 Android Debug 证书（`CN=Android Debug, O=Android, C=US`）。这说明这次发布确实用了 release key；只要 secret 在，日常发布不受影响。本条说的是两个风险：secret 缺失时静默回退（缺守卫）、以及私钥没有离线副本（灾难恢复）。GitHub Secrets 无法从仓库读取，这里是从产物反推；更早的 1.x 版本未逐版核验（证书有效期从 2026-06-07 开始）。

### 2.5 产品完成度

| 功能 | 现状 | 问题 |
|---|---|---|
| 书签 | 只能"添加"，SnackBar 提示成功 | `BookmarkService.loadAll/forDocument/remove/update` 无任何 UI 调用方；不能查看、跳转、删除、写备注 |
| 阅读历史 | 每次打开都 `record()` | 从未展示；`recentEvents()` 无调用方；书库"最近阅读"用的是另一套 `recentOpenedAt` |
| 数据可携带性 | 无导出、无备份 | 卸载、换机、清数据 = 全部丢失；3.0 明确不做，改为在 README/首启/关于页写清"数据仅在本机" |
| 删除 | 直接删，无确认、无撤销 | 单个删除无确认无撤销；批量删除有确认（不一致） |
| 全文搜索 | 只有标题/类型/路径/标签/大小/状态的过滤 | `_matchesQuery` 不碰正文；"找一句话"只能先打开文档再搜 |
| 文件夹导入 | 扁平化，每个文件单独一个镜像目录 | 目录结构丢失；只复制 `.md/.html`，图片/CSS/附件不复制 |
| 导入语义 | README 说"导入就是引用，不复制文件"；Android 实际把文件复制到 `filesDir/referenced_documents`，再标成 `isReferenced=true` | 存储翻倍；"引用"与"副本"混用，正是删除语义、路径键、孤儿数据一系列问题的根源 |
| 相对资源 | 按镜像目录解析 | 导入带图片的笔记，图片全部 broken；HTML 的本地 CSS 同样 |
| 文档内锚点 | `#heading` 交给 `launchUrl` | 打不开或跳到浏览器；跨文档 `.md` 链接也不支持 |
| 分享/导出 | 无 | 3.0 不做；文档来自用户原件，可在源应用里分享 |
| 阅读统计 | 无 | 历史数据白存 |
| 多语言 | 仅中文，`locale` 强制 `zh_CN` | 系统英文环境也显示中文；约 321 条硬编码没有抽取层 |
| 平板/横屏 | 横屏有 Rail 侧栏 | 无阅读页/列表双栏；横屏导航文案与竖屏不一致（"首页"/"文库"） |

**判断**：2.x 的功能是"按需长出来的"，不是"按闭环设计的"。3.0 不需要更多功能，需要把已有功能**收口**，再补两个真正缺的：文档包、数据出口。

### 2.6 体验与可访问性

- **对比度不达标**：`AppColors.inkMuted48`（`#7A7A7A`）在 `#FFFFFF` 上 4.29:1、在 `#F5F5F7` 上 3.94:1，低于 WCAG AA 对正文的 4.5:1；HTML 徽标色 `#E67E22` 与白底/白字仅 2.85:1。14px 的 `bodyMedium` 大量使用这个灰色。
- **动态字体没有适配**：全仓 0 处 `textScaler`；头部 `GlassToolbar(height: 72)`、书库顶部 padding `82`、最近阅读卡 `height: 122`、书架 `childAspectRatio: 0.72` 都是硬尺寸。系统字体调到 1.6–2.0 时，头部会撑破、首卡被压。
- **"减弱动效"没有接**：0 处 `disableAnimations`；卡片弹簧、12 项级联入场、骨架扫光、Tab 共享轴、阅读进度的 `animateTo` 全部无视系统开关。
- **阅读进度条实际不可见**：`Scaffold(extendBodyBehindAppBar: true)` 的 body 第一个子节点是 3px 的 `_ReaderProgressBar`（`reader_page.dart:447-449`、`791-829`），落在状态栏/AppBar 之下；经典模式被不透明 AppBar 完全盖住。README 的"顶部进度条"名不副实。
- **HTML 是二等公民**：`_buildBody` 直接返回 WebView，`SmartScrollbar` 不在树里，`reportScroll()` 恒为空；`_buildExternal` 64 行是死代码。HTML 只剩 WebView 自带的滚动行为，没有 Markdown 那套跟随主题、可拖拽的滚动条。
- **HTML 加载失败会无限转圈**：`NavigationDelegate` 只有 `onPageFinished`，没有 `onWebResourceError`/超时；渲染进程 OOM 时 `_isLoading` 永远 true。
- **破坏性操作不一致**：单个"移出"直接执行，无确认、无撤销；批量"移出"有确认对话框。
- **错误不可恢复**：首次扫描失败只显示一条不可关闭、不可重试的错误条；阅读页错误页没有"重试/重新授权"按钮，只能退出。
- **TOC 当前项是估算**：`progressRatio * entries.length` 不是标题真实位置，标题密度不均时高亮错行；书签标题也用同一套算法。
- **点击区域偏小**：玻璃模式的 AppBar 动作声明 `GlassIconButton(size: 40)`，低于 Material/无障碍建议的 48dp（实际命中区需实测）；经典模式是 48dp，两种模式手感不同。
- **错误文案靠字符串匹配**：`document_error_describer.dart:4-27` 用 `contains('不存在')`、`contains('权限')` 判断类型，平台/localized 文案一变就失效；应改成类型化错误。

### 2.7 性能与包体

- **字体是最大单项**：`assets/fonts/LXGWWenKai-Regular.ttf` 25,575,676 字节（24.4 MiB），约占仓库 asset 体积的 98%；实测 GitHub Release 的 `v2.9.9+199` APK 为 37,206,614 字节（35.5 MiB）。LXGW WenKai 为 OFL-1.1，仓库内没有随附授权文本（以字体官方声明为准），分发合规待补。
- **文档上限 100 MB 且全量读入**：`DocumentFileRules.maxReadableBytes = 100MB`；Markdown 解析、HTML 样式化都会把全文读进内存，再复制到 isolate。2 GB 内存设备打开 50–100 MB 文档有 OOM 风险。
- **双渲染管线**：Markdown 走 `flutter_smooth_markdown` 的分段虚拟化，HTML 走 WebView；TOC、搜索、进度、滚动条各有一套实现。功能要写两遍，测试要测两遍。
- **扫描是串行的**：每个文件 `stat`、每个引用文档每 5 分钟一次 MethodChannel 往返；几百个文档时首屏会慢。
- **做得好的地方**：WebView 的滚动桥用 `requestAnimationFrame` + 0.0005 阈值 + passive listener（`html_document_view.dart:195-224`），比大多数实现克制；玻璃材质有明确的 blur 预算和质量分级。

### 2.8 文档与协作

**强项**：`AGENTS.md` 把边界、约束、发布流程写得很清楚；`docs/release.md` 有授权、TLS 例外、手动兜底；README 的用户视角完整；Actions 全部按 SHA 固定；`pubspec.lock` 提交并使用 `--enforce-lockfile`；仓库未跟踪 keystore/key.properties。

**缺口**：
- 没有 `ARCHITECTURE.md`、`CONTRIBUTING.md`、`SECURITY.md`、`ROADMAP.md`、issue/PR 模板；变更记录只有 `updatelog.md`，且已过期。
- `updatelog.md` 停在 2.9.5，2.9.6–2.9.9 没有记录；tag 缺 `+195`–`+198`。
- 字体、emoji 数据的授权说明缺失。
- 应用内没有隐私说明页；README 的"不经过服务器"与 `allowBackup` 默认值冲突。
- 没有"如何本地跑起来"的开发者文档——因为作者机器没有 SDK，CI 是唯一门禁。这是**流程风险**，不只是文档缺失。

### 2.9 根因：为什么一个审美在线的项目，工程可信度只有 2.6

- **反馈回路太长**：作者机器没有 Flutter SDK，UI 改动只能"提交 → 等 CI → 装机看"。像"72dp 头部在 2.0 字体下溢出""进度条被 AppBar 盖住"这种问题，写代码时根本看不见。
- **版本节奏把发布日常化**：199 个 build、73 次提交，几乎每次修复都是一次 release。发布多了，发布前的检查就少了；tag/changelog 的缺口就是证据。
- **功能按需生长，出口滞后**：书签、历史都是"先把数据写进去"，"读出来"的页面一直没排上；文件夹导入先解决"能选"，"资源完整"后置。
- **结构给速度让路**：AGENTS 已经写了"新逻辑放新文件"，但四个 1,000+ 行的热点仍在长；`part` 让"拆文件"看起来完成了，实际没有解耦。
- **测试跟着功能走，而不是跟着风险走**：解析器、玻璃预算有测试（因为好测），导入、删除、更新没有（因为难测）——恰好后者才是会丢数据的地方。

这不是"能力问题"，是"反馈回路 + 节奏"的问题。3.0 的工程部分，本质上是把反馈回路缩短、把发布节奏降下来。

## 3. 3.0 定位与范围

### 3.1 一句话

> **简兮 3.0：把你散落在手机里的 Markdown 笔记，变成一个读得完、找得到、不丢的本地知识库。**

这句话对应三个动词，也对应三个必须交付的能力：

- **读得完**：文档包（目录、图片、附件、相对链接、锚点）——补上"格式原貌"的最后一块。
- **找得到**：阅读痕迹（书签/笔记/历史）+ 库级全文搜索——从"打开一个文件"变成"使用一个库"。
- **不丢**：安全底线（删除可撤销、迁移可回退、损坏不扩散）——应用自身不弄丢用户的数据；卸载/换机仍需用户自己保留源文件。

**3.0 的 30 秒演示（发布前按这个走一遍）**：

1. 导入一个 50 篇笔记 + 100 张图片的文件夹；图片、附件、相对链接、`#锚点` 直接可用。
2. 在库里搜一个词；跨文档结果带上下文片段；点进去命中高亮。
3. 加一个书签；退出重进；从书签跳回。
4. 删一个文档；10 秒内撤销。
5. 从 2.9.9 升级；文档/标签/书签/进度完整。

这 5 步里任何一步不成立，3.0 就只是"2.9.10 换了个号"。

### 3.2 战略选择：为什么是"本地知识库"，不是"AI 阅读助手"

| 定位 | 3.0 该做什么 | 上限 | 风险 |
|---|---|---|---|
| A. 纯阅读器 | 更快的渲染、更多格式、更稳 | 低：很容易被系统文件预览/浏览器替代 | 功能同质化 |
| **B. 本地知识库（推荐）** | 文档包、检索、痕迹、安全底线 | 高：越用越离不开，迁移成本是护城河 | 数据层工作量大 |
| C. AI 笔记终端 | 对话、总结、生成 | 高，但拥挤 | 破坏 local-first；模型成本/隐私/合规 |

选 B 的理由：简兮的差异化不是"能读"，是"干净、离线、数据是自己的"。C 会把最强的承诺（不经过服务器）变成最弱的环节；A 的天花板又太低。B 则能把现有资产（渲染、排版、玻璃、导入）全部复利。

### 3.3 范围：3.0 做什么、不做什么

| 能力 | 用户场景 | 为什么进 3.0 | 预估 | 可裁剪性 |
|---|---|---|---:|---|
| **A. 文档包** | 导入一个 Obsidian/Codex 笔记文件夹，图片、附件、`[链接](other.md)`、`#标题` 都能用 | 直接修复"格式原貌"承诺；需要存储模型升级，天然属于大版本 | 2.5 人周 | 不可裁 |
| **B. 阅读痕迹** | 书签列表、笔记、历史时间线，一键回到那句话 | 把已写入的数据变成功能；是留存最直接的抓手 | 1.5 人周 | 不可裁（可先只做书签列表） |
| **C. 安全底线** | 误删可撤销、升级可回退、损坏不扩散 | 没有它，A/B 的数据模型升级就是裸奔；但它不需要新的页面 | 0.5–1 人周 | 不可裁 |
| **D. 全文搜索** | 输入"缓存失效"，直接看到 3 篇文档里的上下文并跳转 | 从"阅读器"变成"知识库"的关键；CJK 需要专门处理 | 2.5 人周 | 不可裁（砍 D 就不是 3.0） |
| **E-min. 发布守卫** | 签名硬失败、`apksigner` 指纹、APK SHA256、版本 fail-closed | 不是新功能，是 1.5 天就能补上的"不发错包"底线 | 0.3 人周 | 不可裁 |
| **F-min. 测试底线** | 迁移、损坏、删除、搜索索引单测 + 5 条黄金路径 + CI Android 构建 | 让 A–D 敢改；不追求全量覆盖率，只覆盖会丢数据的路径 | 2 人周 | 不可裁 |
| **G. 3.0 呈现** | 首启"3.0 能做什么"、文件夹导入入口、全文搜索入口、changelog | 功能做了但用户找不到，等于没做 | 0.5 人周 | 不可裁 |

**文档包的两种实现（3.0 必须先定）**：

- **复制成包（默认）**：把目录、文档、资源复制到应用存储，保留相对路径；离线稳定、数据在应用内可整体拷贝。
- **原地引用（3.1）**：通过 SAF tree URI 直接读用户目录，不复制；代价是权限失效、外部修改、URI 解析与性能复杂度。

3.0 先做"复制成包"，并在导入时明确告诉用户"会复制到应用内，原文件不会被修改"；不要再用一个 `isReferenced` 同时表示"引用"和"镜像副本"。

**明确不做（3.0）**：

- 用户可见的备份中心、定时备份、回收站页面、数据导出：没有编辑功能，文档来自用户原件；只保留应用内部的安全快照与删除撤销，不新增页面。
- 云同步/账号体系：与"不经过服务器"冲突，且是另一个产品。
- AI 对话/总结：成本、隐私、合规都不在一个人能扛的范围内。
- EPUB/PDF：渲染沼泽，会把 3.0 拖成 4.0。
- iOS：没有 Mac/CI，且当前交互（左边缘返回、玻璃）需要重做。
- 状态管理重写（Riverpod/Bloc）：收益低、风险高；保留 Provider，拆控制器即可。
- 液态玻璃重做：视觉已经是资产，3.0 只做"冻结 + 可访问性回退"。

### 3.4 决策点（大部分已定）

1. **周期**：接受 9–14 周（激进 9–11，一个人 12–14），还是走 2 周止血的 `2.10.0`？
2. **数据模型**：已定做 schema v1 + docId，但用"只增不删 + 双读回退"，旧文件保留一个版本。
3. **搜索**：已定进 3.0（D 不可裁）；时间不够时砍 B 的笔记编辑，不砍 D。
4. **桌面端**：已确认仅 Android（2026-10-29）。删除 `windows/`、`web/` 与非 Android 导入/删除分支，非 Android 环境直接 fail-fast。
5. **字体**：子集化（推荐，24.4 MiB → 约 5–7 MiB）还是移除内置字体、改用系统字体？
6. **语言**：3.0 明确"仅中文"，还是抽字符串层为 3.1 的英文做准备？（建议后者，但不在 3.0 翻译）

> 已定（2026-10-29）：不做用户可见的备份/导出/回收站；保留"删除确认 + 撤销、迁移内部快照 + 双读回退、损坏隔离"。

## 4. 工程地基：3.0 必须完成的结构调整

原则：**收口，不重写。** 2.x 的视觉与渲染资产很贵，3.0 只做"把边界画清楚、把数据搬正、把测试补上"，不做 big-bang rewrite。

### 4.1 分层与依赖规则

```text
lib/
  app/                    # bootstrap、DI、路由、主题装配
  core/                   # design tokens、通用组件、错误、日志、工具
  data/
    documents/            # 文档仓储、扫描、导入、文档包、镜像
    metadata/             # 版本化存储、迁移、内部快照、删除撤销
    search/               # 索引、查询、片段
    platform/             # SAF / MethodChannel 网关
  features/
    library/              # 列表、搜索、选择、导入 UI
    reader/               # 阅读页 + 两个渲染适配器
    traces/               # 书签、笔记、历史
    settings/
```

四条硬规则：

1. `core/` 不 import `features/` 或 `data/`。
2. `features/` 只能 import `core/` 和 `data/` 的**接口**，不能 import 另一个 feature 的内部实现。
3. 不再新增跨目录 `part`；单文件超过 400 行就拆。现有 `part` 单元按 feature 边界机械拆分，一次一个 PR。
4. 每个 feature 暴露一个 `feature.dart` barrel，外部只允许从 barrel 进入。

### 4.2 数据层：从"路径键"到"文档 ID + 版本化存储"

**目标模型**：

```text
metadata/
  library.json      {schema: 1, updatedAt, documents: [...], tags: [...], marks: [...]}
  progress.json     {docId: ratio}                 # 高频、低价值、丢失可接受
  search/<docId>.idx                               # 可重建
  backups/v<schema>-<ts>/...                       # 迁移前内部快照，不暴露给用户
```

- **主键**：每个文档一条 UUID；`sourceUri` 只做唯一约束/查重；`path` 是可变的普通属性。标签、置顶、最近打开、进度、书签、历史全部外键到 `docId`。
- **单一写入者**：所有元数据变更走 `MetadataStore.transaction()`；一次删除 = 一个事务内改 `documents/tags/marks`，随后清 `progress` 与索引。`progress.json` 允许独立、低频写。
- **版本与迁移**：`schema` 字段 + `MigrationRunner`（v0→v1）；迁移前把 `metadata/` 复制到 `backups/`（内部快照）；迁移只增不删，旧文件保留一个版本。
- **双读回退**：启动时优先读新存储；新存储缺失或损坏时回退读旧 JSON/prefs，并重新生成新存储。这样坏版本还能退回 2.9.9。
- **损坏容错**：逐条 `try/catch`，坏条目丢弃并计数；整文件解析失败先 `copy` 成 `*.corrupt-<ts>`，再重建空库并提示"已隔离损坏文件，可排查"。**绝不静默覆盖。**
- **删除可撤销（不做回收站页面）**：删除前确认；删除时把文件移入 `.trash/<ts>/`，SnackBar 提供 10 秒"撤销"；启动时清理超过 24 小时的条目。
- **无用户导出**：文档以副本形式留在应用存储；README、首启、关于页明确"数据仅在本机，卸载或换机即丢失，请自行保留源文件"。
- **孤儿 GC**：启动后低优先级巡检 `documents × marks × progress × search`，输出计数并清理；路径失效保留"文件缺失"占位，不静默丢条目。

**技术选型建议**：3.0 先用"单文件 JSON + 临时文件 rename + 迁移器"，不要为了搜索引入 SQLite 全家桶。等文档数超过 ~1,000、或需要复杂查询时，再把 `MetadataStore` 的实现换成 SQLite/Drift——接口不变。搜索索引单独放 `search/`，可随时重建，不参与事务。

### 4.3 阅读内核：一个接口，两个适配器

现在 Markdown 和 HTML 各自实现 TOC、搜索、进度、滚动条，导致 HTML 天然是二等公民。3.0 抽一个接口：

```dart
abstract interface class ReaderEngine {
  Future<void> load(Document doc, ReaderStyle style);
  Future<List<TocEntry>> toc();
  Future<SearchMatches> search(String query);
  Future<void> jumpTo(ReaderAnchor anchor);   // 标题 / 比例 / 搜索命中
  ValueListenable<double> get progress;
  Widget buildView(BuildContext context);
}
```

- `MarkdownEngine` 包现有 `MarkdownViewer`；`HtmlEngine` 包现有 `HtmlDocumentView`。
- TOC 高亮、搜索、进度、滚动条上移到共享 controller，两个引擎只负责"渲染 + 报告位置"。
- 不改渲染器本身；这是**适配器模式**，不是重写。

### 4.4 状态与错误

- 每个页面一个显式状态机：`idle / loading / ready / empty / error`；所有异步回调写状态前校验 `requestId`，旧请求只能被丢弃，不能留下 loading。
- 错误类型化：`DocumentFailure`（`notFound`、`permissionDenied`、`tooLarge`、`unsupported`、`io`、`corrupt`），UI 按类型给动作（重试/重新授权/换文件），不再 `contains('不存在')`。
- 保留 Provider + `ChangeNotifier`；把 `LibraryController` 拆成 `LibraryController`（列表/查询）、`ImportController`（导入状态）、`SelectionController`（多选），避免一个 546 行类承担所有状态。

### 4.5 测试与 CI

**测试金字塔**：

| 层 | 内容 | 目标 |
|---|---|---|
| 单元 | 迁移、索引、锚点解析、文件名规则、仓储事务、错误映射 | 快、纯 Dart，数量占 70% |
| Widget | 书库/阅读/痕迹/设置，使用 fake repository | 状态与交互，占 20% |
| 集成 | 5 条黄金路径（见下） | 真机/模拟器，占 10% |
| Golden | 3 个页面 × 明暗 × 1.0/1.3 字体 | 防视觉回归 |

**5 条黄金路径**：

1. 导入含 20 张图片、5 个跨文档链接的文件夹 → 全部渲染 → 点链接跳转 → 返回。
2. 打开读到 60% → 退出 → 重进 → 进度保留 → 加书签 → 从书签跳回。
3. 库级搜索"缓存" → 3 条结果 → 点进第 2 条 → 高亮命中 → 返回搜索。
4. 删除文档 → 10 秒内撤销 → 数据完整；再次删除 → 24 小时后清理，不出现回收站页面。
5. 用 2.9.9 的旧数据启动 3.0 → 迁移 → 只保留旧文件 → 模拟新存储损坏 → 回退读旧存储，数据仍可读。

**CI 增量**：

- `android-build` job：PR 上构建 release APK（临时 keystore），`aapt2 dump badging` 断言 `versionCode`、权限、`allowBackup`、`minSdk/targetSdk`。
- `coverage` job：`flutter test --coverage` + `lcov` 阈值；核心域 ≥60%，整体 ≥35%，diff ≥70%。
- `integration` job：Android emulator 跑 5 条路径（可 nightly，PR 只跑 2 条快的）。
- `analyze` 加严：`strict-casts`、`strict-raw-types`、`unawaited_futures`；0 `ignore:`。

### 4.6 可观测性（不上报）

- 本地环形日志（最近 500 条，含时间/模块/错误码，路径脱敏），设置页"导出诊断信息"。
- `FlutterError.onError` / `PlatformDispatcher.onError` 写入同一日志；崩溃后下次启动提示"上次异常已记录，可导出"。
- 不做遥测、不上传；用 GitHub issue 模板引导用户附诊断包。这既守住隐私，也解决"发布后一无所知"。

## 7. 发布、迁移与回滚

### 7.1 版本策略

- `3.0.0+300` 是 3.0 的正式 build；alpha/beta/rc 用 290–299（如 `3.0.0-beta.1+295`、`3.0.0-rc.1+299`），保证 versionCode 单调、可升级到 300；之后 `3.0.1+301`、`3.1.0+3xx`，**build 号只增不减**（更新检查依赖它）。
- 单一版本源：`pubspec.yaml`。`about_settings.dart` 的 fallback 与 workflow 的文件名都从它派生（脚本生成 `build_info.dart`，或构建时 `--dart-define`），不再手写第二份。
- 每个发布 tag 必须指向实际构建的 commit；`publish.yml` 的 `outputs.sha` 改为 checkout 后 `git rev-parse HEAD`，而不是 `github.sha`。
- tag 格式保持 `v<version>+<build>`；changelog 由发布流程自动写入 `updatelog.md`，不再让发布说明与仓库两份记录各说各话。

### 7.2 通道与灰度

- 更新接口增加 `channel=stable|beta`；Beta 只在小范围（QQ 群/自用）传播。
- 发布顺序：`3.0.0-beta.1+295`（1 周）→ `3.0.0-rc.1+299`（3–5 天）→ `3.0.0+300`。
- 更新服务器保留**至少两个** APK：当前稳定版 + 上一稳定版；响应头带 `x-apk-sha256`、`x-apk-build`、`x-apk-min-supported`。
- 客户端对 `x-apk-sha256` 做校验；缺失即拒绝安装（fail-closed）。Android 安装器本身会校验签名，但"先校验再交给安装器"能挡住损坏包和降级包。

### 7.3 迁移演练矩阵

| 维度 | 取值 |
|---|---|
| 来源版本 | 2.9.5 / 2.9.9（各一份真实数据） |
| 数据规模 | 10 文档 / 200 文档 / 500 文档 |
| 异常数据 | 损坏的 bookmarks.json / 截断的 history.json / 丢失的 id_map |
| 系统 | Android 7、10、12、14、16 |
| 设备 | 2 GB 低端、4 GB 中端、8 GB 高端 |
| 显示 | 默认字体、2.0 字体、深色、横屏 |
| 存储 | 内部存储、SAF 引用、外置 SD |

每格记录：启动时间、迁移耗时、丢失条目数、首屏是否可用、日志中的异常。**任何一格丢失 >0，停止发布。**

### 7.4 回滚

- 保留 `2.9.9+199` 的 APK 与更新服务器入口；`x-apk-min-supported` 可把 3.0 标记为"不强制"；alpha/beta 的 APK 只在测试群留存。
- 发布私钥已无离线副本，仅存 GitHub Secret；**禁止删除/轮换/迁移**。丢 key = 老用户必须卸载重装（本地书签/进度丢失）。
- 3.0 迁移前自动做 `metadata/` 内部快照；若迁移失败，应用进入"只读安全模式"，提示保留源文件并反馈，不写坏数据。
- 回滚不是"降级安装"（Android 不允许），而是"发一个 3.0.1 修复版"；所以 3.0.0 必须有"远程止损"能力：服务端把坏版本标记为 `revoked`，客户端检查到后提示"请安装修复版"。
- `docs/release.md` 增加"回滚演练"章节：模拟一次坏版本发布，从标记 revoke 到用户看到提示，全流程走一遍。

### 7.5 发布前 24 小时 Runbook

1. `pubspec.yaml` bump；同步 fallback；写 `updatelog.md`；提交 `(build N)`。
2. CI 全绿；确认 tag 指向 HEAD；确认 workflow 实际构建的 commit 与 tag 目标一致。
3. 构建：`gh secret list` 确认 `RELEASE_KEYSTORE` 存在；`apksigner verify --print-certs` 指纹与上一版一致；记录 SHA256。
4. 三台设备：2.9.9 → 3.0 升级；检查文档/标签/书签/进度/删除撤销。
5. 发布 pre-release；24 小时观察 issue/群反馈；只修 P0。
6. 转正式；上传更新服务器；回读接口确认 `build/sha256` 正确；保留旧 APK。
7. 发布后 72 小时：监控"更新失败/数据丢失"关键词；准备 3.0.1。

### 7.6 3.0 发布后 90 天的成功标准

- 数据丢失类 issue = 0；书签/进度/"图片不显示"类 issue 较 2.9.x 明显下降。
- 更新失败类反馈 < 1%（以更新服务器日志与群反馈为准）。
- 至少 10 个真实文件夹导入案例，图片、附件、相对链接 100% 正确。
- 新用户 5 分钟内能走完"30 秒演示"的 5 步；至少 3 个真实用户复现成功。
- 包体 < 30 MB，冷启动 < 1.5s（中端机），搜索 p95 < 300ms。
- 卸载/换机导致的数据丢失不在 3.0 承诺内；README、首启、关于页三处写明"数据仅在本机"，这类反馈按说明处理，不按缺陷处理。
- 3.0.x 进入稳定期：只修 P0/P1，不再加功能；3.1 才开新能力。

### 7.7 发布密钥现状与约束（2026-10-29 确认）

- 原始 release keystore 没有离线副本；本机只有 `~/.android/debug.keystore`，不是发布 key。
- 唯一可用的私钥副本是 GitHub Actions Secret `RELEASE_KEYSTORE`；`v2.9.9+199` 的 APK 已证明它可用。
- GitHub Secret 只写、不可读，无法导出，也无法复制到另一个仓库/账号。
- **3.0 仍可发布**：只要仓库、账号、secret 都在，CI 每次都能签出正常 release 包。
- 但签名身份**不可再生**。以下操作禁止：
  - 删除/覆盖 `RELEASE_KEYSTORE`；
  - 轮换签名 key（除非先设计好用户迁移）；
  - 转移/删除仓库，或让仓库/账号失效（secret 可能不随仓库转移）；
  - 在未确认 secret 存在时发布。
- 必须做：
  - 账号 2FA + recovery codes；仓库至少两个 admin；
  - `publish.yml` 在 secret 为空时硬失败；
  - 每次发布 `apksigner verify --print-certs`，指纹必须是 `b76b05e9…`；
  - 发布前 `gh secret list` 确认五个 secret 名称都在。
- 如果 secret 丢失：现有用户无法覆盖安装。可选：
  1. 停止更新，保留当前版本；
  2. 新包名并列发布（用户手动迁移，旧 app 保留）；
  3. 同包名换新 key，用户卸载重装——书签/进度/标签会丢，因为 3.0 不做导出。
